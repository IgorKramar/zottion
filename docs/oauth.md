# Собственный OAuth-сервис

Автор: Igor Kramar. Один экземпляр `zottion-auth-service`, Axum/Tokio.
Нужна зарегистрированная public connection Notion с фиксированным callback
`https://YOUR_AUTH_HOST/callback`. Production-домен, сертификат и размещение
настраиваются отдельно.

Окружение сервиса:

| Переменная | Назначение |
|---|---|
| NOTION_CLIENT_ID | ID public connection |
| NOTION_CLIENT_SECRET | Секрет из менеджера секретов, только на сервере |
| ZOTTION_OAUTH_CALLBACK_URL | Фиксированный callback с путём /callback |
| ZOTTION_OAUTH_BIND | По умолчанию 127.0.0.1:9393 |

```sh
cargo run --release -p zottion-auth-service --locked
zottion --timeout 300 auth login --server https://YOUR_AUTH_HOST
zottion auth status --json
zottion auth refresh
zottion auth logout --revoke
```

Не передавайте секреты аргументами и не помещайте их в repo/config.toml.
Клиент принимает только HTTPS URL; HTTP разрешён для loopback в локальной
разработке. Для него callback может быть `http://127.0.0.1:9393/callback`,
если такой URI разрешён настройками connection.

## Протокол

1. Клиент создаёт случайный verifier и отправляет SHA-256 challenge в
   `POST /sessions`; сервис выдаёт ID и официальный URL авторизации Notion.
2. Случайный state связывает callback с сеансом. Callback резервируется до
   обмена кода, поэтому параллельные/повторные callbacks отклоняются.
3. Сервис обменивает код на `/v1/oauth/token` с Basic client ID/secret и
   фиксированным redirect URI. Ошибочный или истёкший state отклоняется.
4. Клиент опрашивает `POST /sessions/{id}/result` с verifier в JSON. Пока вход
   не закончен — 202; правильный verifier получает пару токенов однократно.
   Повторная выдача, неверный verifier и истёкший сеанс отклоняются.
5. Клиент сохраняет access/refresh одной записью в системном хранилище.
   Страницы затем идут напрямую в официальный API, минуя сервис авторизации.
6. `/refresh` и `/revoke` выполняют соответствующие операции Notion. Обмен
   кода, ротация и отзыв после неоднозначной сетевой ошибки не повторяются
   автоматически. После потерянного результата ротации нужен новый вход.

Сеансы живут до пяти минут, максимум 1024 одновременно. Состояние находится
в памяти: рестарт сервиса требует нового входа для незавершённых сеансов.
Все ответы имеют no-store; verifier не попадает в URL. При ротации проверяется
workspace/bot identity, а локальная блокировка профиля сериализует обновление
токенов между процессами. Открытый файл вместо недоступного keychain не создаётся.

## Эксплуатация и проверка

TLS завершайте на reverse proxy. Отключите журналирование query callback,
Authorization и тел запросов/ответов; в них могут быть коды и токены.
Сам сервис не печатает их в диагностику. Он является доверенным компонентом:
видит токены при обмене, хотя не получает содержимое страниц.

Перед публичным входом проверьте реальный браузерный сценарий, Secret Service
и Keychain, истечение сеанса, отзыв в Notion и ротацию пары. Автотесты протокола
используют локальный provider и не заменяют эту проверку. После рестарта
проверьте новый login; при сбое ротации начните login заново.

После запуска ожидаются успешные login/status и прямое чтение клиента.
Сигналы отказа — ошибки входа, повторные 401 и рост 429; сначала проверьте
callback/доступность провайдера и лимиты. Содержимое страниц и токены в
логи не добавлять. При утечке отзовите connection в Notion и смените секрет;
при ошибке обновления сервиса верните предыдущий бинарник и начните вход заново.
