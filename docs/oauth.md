# Собственный OAuth-сервис

Автор: Igor Kramar. Один экземпляр `zottion-auth-service`, Axum/Tokio.
Это вариант браузерного OAuth для владельца своего сервиса. Для личного
workspace можно обойтись без сервиса: `auth login --token-stdin` сохраняет
API-токен в системном keychain. Все три пути описаны в
[README](../README.ru.md#авторизация).

Нужна зарегистрированная public connection Notion с фиксированным callback
`https://YOUR_AUTH_HOST/callback`. Production-домен, сертификат и размещение
настраиваются отдельно.

Окружение сервиса:

| Переменная | Назначение |
|---|---|
| NOTION_CLIENT_ID | ID public connection |
| NOTION_CLIENT_SECRET | Секрет из менеджера секретов, только на сервере |
| ZOTTION_OAUTH_CALLBACK_URL | Фиксированный callback с путём /callback |
| ZOTTION_OAUTH_BIND | По умолчанию 127.0.0.1:9393 |

```sh
cargo run --release -p zottion-auth-service --locked
zottion --timeout 300 auth login --server https://YOUR_AUTH_HOST
zottion auth status --json
zottion auth refresh
zottion auth logout --revoke
```

Не передавайте секреты аргументами и не помещайте их в repo/config.toml.
Клиент принимает только HTTPS URL; HTTP разрешён для loopback в локальной
разработке. Для него callback может быть `http://127.0.0.1:9393/callback`,
если такой URI разрешён настройками connection.

## Вход без обязательного --server

`zottion auth login` выбирает сервис в таком порядке:

1. Явный `--server URL`.
2. Переменная `ZOTTION_AUTH_SERVER`.
3. Сервер последнего OAuth-входа в выбранном profile/workspace.
4. Публичный адрес, заданный при сборке через `ZOTTION_DEFAULT_AUTH_SERVER`.

Например, первый вход в свой сервис:

```sh
ZOTTION_AUTH_SERVER=https://YOUR_AUTH_HOST zottion auth login
zottion auth login
```

После успешного входа второй вызов использует сохранённый адрес. Адрес без
успешного входа не сохраняется. Приоритет профилей и `--workspace` остаётся тем же;
`refresh`/`logout --revoke` всегда используют сервер сохранённой пары токенов,
а не новый адрес из окружения. Неверный URL не заменяется другим скрыто.
Браузерный вход ждёт до 300 секунд; `--timeout` задаёт свой срок. Для API-команд
и `--token-stdin` по умолчанию остаётся 30 секунд.

Постоянный публичный адрес пока не выбран: обычная сборка без настроенного
сервера возвращает понятную ошибку с кодом 3. Адрес страницы Notion сервисом
авторизации не становится. API-токен и `NOTION_TOKEN` продолжают работать
независимо от настроек OAuth-сервера.

## Подготовленное размещение на Render

[render.yaml](../render.yaml) описывает один постоянно работающий native Rust
сервис, Rust 1.91.0, `/health` и отключённые автоматические развёртывания.
Docker, БД и диск ему не нужны. Файл сам по себе ничего не создаёт и не оплачивает.
План `0.5c-512mb` стоит **$7 в месяц за compute** на 30 октября 2026 года;
платные дополнительные возможности и превышение включённых лимитов в эту сумму
не входят. Достаточно базового workspace; Pro для приложения не требуется.
[Тарифы](https://render.com/pricing), [спецификация Blueprint](https://render.com/docs/blueprint-spec).

Render предоставляет собственный HTTPS-поддомен `onrender.com`, поэтому
покупать домен отдельно не обязательно. При запуске Blueprint нужно задать
`NOTION_CLIENT_ID`, `NOTION_CLIENT_SECRET` и точный callback
`https://ASSIGNED_HOST/callback`, зарегистрированный в public connection Notion.
Секрет вводится в панели Render; не добавляйте его в YAML, GitHub variables,
README или параметры команд. Если хост ещё не назначен, сначала создайте сервис,
затем завершите настройку переменных и запустите развёртывание вручную.
[Web services](https://render.com/docs/web-services),
[фиксированный redirect URI Notion](https://developers.notion.com/guides/get-started/authorization).

Порядок включения публичного входа:

1. Подтвердить размещение/стоимость, создать сервис, получить постоянный URL.
2. Создать public connection с нужными capabilities и зарегистрировать callback.
3. Задать три серверные переменные в панели, вручную развернуть нужный коммит.
4. Проверить `GET /health`: HTTP 200, `{"status":"ok"}`, `Cache-Control: no-store`.
   Это проверка процесса, а не доказательство исправных OAuth credentials.
5. Выполнить живые login/status, прямое чтение Sandbox, refresh и revoke в
   отдельном `--profile oauth-check`; существующий вход не затрагивать.
6. После успешной проверки задать GitHub repository variable
   `ZOTTION_AUTH_SERVER` с корневым HTTPS-адресом и запустить workflow `packages`.
   Он встраивает адрес в готовые клиентские архивы. Для `cargo install --git`
   адрес передают через build-time `ZOTTION_DEFAULT_AUTH_SERVER` либо runtime
   `ZOTTION_AUTH_SERVER`: переменные GitHub автоматически туда не переносятся.

Не включайте HTTP request logs с callback query и тела запросов. Render
добавляет request logs на workspace Pro и выше; при смене плана или настройке
log drain отдельно проверьте отсутствие кода callback, Authorization и токенов
в журналах. Приложение само не журналирует запросы.
[Правила логирования Render](https://render.com/docs/logging).

Бесплатный Render подходит для пробного запуска, но засыпает после 15 минут
простоя, а пробуждение занимает около минуты. Для постоянного публичного входа
выбран план без сна. Альтернатива — Railway Hobby: от $5 в месяц с оплатой
использования сверх включённой суммы; тот же бинарник запускается с
`ZOTTION_OAUTH_BIND=0.0.0.0:PORT` и тремя серверными переменными.
[Ограничения Free](https://render.com/docs/free), [Railway Hobby](https://docs.railway.com/pricing/plans).

`/health` не раскрывает настройки или сеансы. Сервис остаётся единственным
экземпляром: несколько процессов без общего хранилища нарушат выдачу сеанса.
После рестарта/обновления незавершённый login нужно начать заново.

## Протокол

1. Клиент создаёт случайный verifier и отправляет SHA-256 challenge в
   `POST /sessions`; сервис выдаёт ID и официальный URL авторизации Notion.
2. Случайный state связывает callback с сеансом. Callback резервируется до
   обмена кода, поэтому параллельные/повторные callbacks отклоняются.
3. Сервис обменивает код на `/v1/oauth/token` с Basic client ID/secret и
   фиксированным redirect URI. Ошибочный или истёкший state отклоняется.
4. Клиент опрашивает `POST /sessions/{id}/result` с verifier в JSON. Пока вход
   не закончен — 202; правильный verifier получает пару токенов однократно.
   Повторная выдача, неверный verifier и истёкший сеанс отклоняются.
5. Клиент сохраняет access/refresh одной записью в системном хранилище.
   Страницы затем идут напрямую в официальный API, минуя сервис авторизации.
6. `/refresh` и `/revoke` выполняют соответствующие операции Notion. Обмен
   кода, ротация и отзыв после неоднозначной сетевой ошибки не повторяются
   автоматически. После потерянного результата ротации нужен новый вход.

Сеансы живут до пяти минут, максимум 1024 одновременно. Состояние находится
в памяти: рестарт сервиса требует нового входа для незавершённых сеансов.
Все ответы имеют no-store; verifier не попадает в URL. При ротации проверяется
workspace/bot identity, а локальная блокировка профиля сериализует обновление
токенов между процессами. Открытый файл вместо недоступного keychain не создаётся.

## Эксплуатация и проверка

TLS завершайте на reverse proxy. Отключите журналирование query callback,
Authorization и тел запросов/ответов; в них могут быть коды и токены.
Сам сервис не печатает их в диагностику. Он является доверенным компонентом:
видит токены при обмене, хотя не получает содержимое страниц.

Перед публичным входом проверьте реальный браузерный сценарий, Secret Service
и Keychain, истечение сеанса, отзыв в Notion и ротацию пары. Автотесты протокола
используют локальный provider и не заменяют эту проверку. После рестарта
проверьте новый login; при сбое ротации начните login заново.

После запуска ожидаются успешные login/status и прямое чтение клиента.
Сигналы отказа — ошибки входа, повторные 401 и рост 429; сначала проверьте
callback/доступность провайдера и лимиты. Содержимое страниц и токены в
логи не добавлять. При утечке отзовите connection в Notion и смените секрет;
при ошибке обновления сервиса верните предыдущий бинарник и начните вход заново.
