# Вход без собственного сервера

Автор: Igor Kramar. Основной браузерный вход использует официальный Notion CLI
`ntn`. Собственные домен, OAuth connection, `client_secret` и хостинг не нужны.
После входа zottion обращается к официальному REST API напрямую.

## Браузерный вход

Установите официальный `ntn` по [инструкции Notion](https://developers.notion.com/cli/get-started/installation).
Проверенная версия — **0.23.25**, Linux x86_64. Native CLI доступен для Linux
и macOS; Node.js нужен только при установке через npm, а не для запуска бинарника.

```sh
ntn --version
unset NOTION_TOKEN
zottion auth login
zottion auth status --json
```

Zottion запускает `ntn login`, затем получает токен через штатный
`ntn auth token --plain`. Токен передаётся внутри процесса, проверяется запросом
`/users/me` и сохраняется в Secret Service/Keychain zottion. В argv, логах и
открытых файлах его нет. Помощник завершается после входа; постоянного локального
процесса нет. Проверяйте совпадение кода в браузере и терминале перед Authorize.

В терминале Notion может предложить уже сохранённый workspace или новый вход.
Для SSH, скрипта или входа в другом браузере:

```sh
zottion auth login --no-browser
```

Откройте напечатанную ссылку и подтвердите код. Zottion сам запускает
`ntn login poll` и ждёт завершения. При отсутствии терминала используется тот же
двухэтапный путь. На цепочку команд помощника по умолчанию отведено 300 секунд; `--timeout`
задаёт общий срок этой цепочки, после которого дочерний процесс останавливается.
Истечение срока возвращает код 6, сбой или отсутствие `ntn` — 3,
отмена Ctrl+C — 130. Режим терминала восстанавливается и после прерванного помощника.

`--workspace` для этого способа — UUID workspace, а не локальная метка.
Ранее выбранный UUID zottion передаёт помощнику и без этого флага; область
сохранения фиксируется на весь вход. Для другого workspace укажите его UUID
явно или начните с нового `--profile`. Локальная метка `default` не передаётся
официальному CLI как UUID.
`--profile` изолирует запись zottion. `NOTION_HOME` позволяет использовать
отдельные настройки официального CLI; этот каталог должен существовать.
Во время запуска помощника принудительно
включены keyring и production; переменные с токеном и альтернативными адресами
`ntn` не переносятся в него. Секреты из `auth.json` не читаются.

Токен действует с правами пользователя в выбранном workspace. Официальный CLI
требует полного членства; guests и restricted members этот вход не поддерживают.
Доступ зависит от Notion и настроек workspace. Для ограниченной connection
или CI остаётся [API-токен](../README.ru.md#api-токен-постоянный-вход).
[Официальный браузерный вход и хранение](https://developers.notion.com/cli/get-started/authentication).

Если `ntn` не установлен или вход не завершён, zottion возвращает явную ошибку.
Открытый файл вместо недоступного keychain не создаётся. Обычный `auth logout`
удаляет запись zottion и сохраняет черновики; `ntn logout` не вызывается, потому
что он удаляет все сохранённые workspaces официального CLI. Новый браузерный
вход выполняется через `auth login`; `auth refresh` и `logout --revoke`
предназначены для дополнительного OAuth-сервиса ниже.

## Ручной перенос из официального CLI

Тот же путь можно выполнить двумя командами. Это пригодится для старой сборки
zottion или уже авторизованного `ntn`:

```sh
ntn login
ntn auth token --plain | zottion auth login --token-stdin
```

Не запускайте `ntn auth token --plain` отдельно, если терминал записывается:
эта команда специально печатает секрет для передачи по pipe. Не используйте
`NOTION_KEYRING=0`. Если задан `NOTION_TOKEN`, уберите его перед импортом:
переменная zottion имеет приоритет над сохранённой записью.

## Дополнительный собственный OAuth-сервис

Этот режим остаётся для владельцев своей public connection и не используется
по умолчанию. Его явно выбирают `--server URL`, `ZOTTION_AUTH_SERVER` либо
ранее сохранённый сервер выбранного profile/workspace. Неверный URL не вызывает
скрытого перехода на другой способ. Секрет connection остаётся у владельца
сервиса. `refresh`/`revoke` используют сервер, сохранённый с парой токенов.

Нужны `zottion-auth-service` и фиксированный callback
`https://YOUR_AUTH_HOST/callback`. В окружении сервиса задаются
`NOTION_CLIENT_ID`, `NOTION_CLIENT_SECRET`, `ZOTTION_OAUTH_CALLBACK_URL`;
`ZOTTION_OAUTH_BIND` по умолчанию равен `127.0.0.1:9393`.

```sh
cargo run --release -p zottion-auth-service --locked
zottion auth login --server https://YOUR_AUTH_HOST
zottion auth refresh
zottion auth logout --revoke
```

Клиент принимает HTTPS; HTTP разрешён для loopback при локальной разработке,
если callback разрешён настройками connection. TLS завершайте на reverse proxy
без журналирования query callback, Authorization и тел запросов/ответов.
Не передавайте секреты аргументами и не сохраняйте в repo/config.toml.

Протокол собственного сервиса: случайный verifier → SHA-256 challenge →
`POST /sessions`; случайный state связывает callback с сеансом. Сервис обменивает
код с Notion через Basic client ID/secret. `POST /sessions/{id}/result` выдаёт
access/refresh по verifier однократно. Неверный state/verifier, повтор и истечение
отклоняются. Пара токенов хранится одной записью keychain; содержимое страниц
через сервис не проходит.

Сеансы живут до пяти минут, максимум 1024 одновременно, только в памяти одного
процесса. После рестарта незавершённый вход начинается заново. Все ответы имеют
no-store; verifier не входит в URL. Обмен, ротация и отзыв после неоднозначного
сбоя автоматически не повторяются. После потерянного результата ротации нужен
новый вход. Реальная проверка этого дополнительного режима остаётся отдельной;
он не требует от проекта содержать общую инфраструктуру.
