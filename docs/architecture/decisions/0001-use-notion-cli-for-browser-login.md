# ADR-0001: Использовать официальный Notion CLI для браузерного входа

- **Date**: 2026-10-30
- **Status**: Accepted
- **Authors**: Igor Kramar

## Context

Проект должен работать на Linux/macOS через официальный REST API. Владелец
исключил расходы на сервер и домен для открытого проекта. Ранее планировалась
общая public connection с отдельным OAuth-сервисом: документированный обмен
кода и обновление токена Notion требуют client_secret. Такой общий секрет
нельзя распространять внутри клиентского бинарника. Временный localhost callback
эту проблему сам по себе не решает.

У официального `ntn 0.23.25` есть браузерный `login`, двухэтапный `login poll`
и явный экспорт `auth token --plain`. Живая проверка подтвердила вход,
сохранение токена в Secret Service и его пригодность для прямого REST-запроса
zottion. Внутренний формат хранилища официального CLI разбирать не требуется.

## Decision

Использовать `ntn` как временный локальный помощник основного браузерного входа.
Zottion получает экспортированный токен по pipe, проверяет `/users/me` и
сохраняет собственную запись в Secret Service/Keychain. Все запросы к страницам
и базам продолжает выполнять клиент zottion напрямую. Общий OAuth-сервис,
домен и платная инфраструктура проекту не нужны.

Сохранить вход через API-токен как самостоятельный способ и дополнительный
явно выбранный OAuth-сервис для владельцев своих connections. Подготовку
Render и встраивание общего серверного адреса убрать.

## Consequences

Браузерный вход не требует общей инфраструктуры или ручного копирования токена.
Секреты не входят в argv/логи/открытые файлы. Помощник имеет общий срок выполнения,
завершается при отмене и не нужен для последующей работы с API.

Появляется отдельная устанавливаемая зависимость `ntn`. Её интерфейс нужно
проверять при обновлениях. Официальный вход требует полного членства в workspace;
guests/restricted members используют другой доступный им способ. Токен работает
с правами пользователя, тогда как internal connection ограничивается отдельно
выданными ей страницами. Политики входа и срок токена зависят от Notion.
На истечение токена отвечаем новым входом; собственную ротацию OAuth для него
не имитируем. `ntn logout` автоматически не вызываем: он удаляет все его
сохранённые workspaces.

## Alternatives considered

1. **Оставить API-токен единственным способом.** Уже работает без инфраструктуры
   и даёт отдельные capabilities/content access. Сохраняем как запасной путь,
   но ручное создание/копирование не обеспечивает нужный браузерный вход.
2. **Содержать общий OAuth-сервис.** Удобен для одной публичной connection,
   но требует постоянного размещения и хранения client_secret. Отклонён
   по прямому ограничению владельца на расходы и инфраструктуру.
3. **Временный localhost OAuth у каждого пользователя.** Снимает размещение
   callback, но при текущем документированном REST-потоке каждый пользователь
   должен создать свою connection и задать client_secret. Сложнее API-токена.
