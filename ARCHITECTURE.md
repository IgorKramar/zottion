# Архитектура zottion

Обновлено: 30 октября 2026 года. Автор: Igor Kramar.

Один Cargo workspace: `zottion` (библиотека и бинарник) и `zottion-auth-service`.
Приняты Rust, официальный REST API `2026-03-11`, Vim по умолчанию, Linux/macOS,
MIT. Граница первой версии описана в [матрице](docs/capabilities.md).

## Границы модулей

```text
TUI (Ratatui/Crossterm + EdTUI) ─┐
                               ├── app ── notion (Reqwest/Tokio) ── Notion
CLI (Clap) ─────────────────────┘    ├── content (raw JSON, разрешённый PATCH)
                                    ├── store (SQLite/FTS5, отдельный поток)
                                    └── auth (профили, Secret Service/Keychain)
```

`app` задаёт одинаковые правила записи для CLI и TUI. Типы PageId/BlockId/
DatabaseId/DataSourceId/ViewId разделены. Исходный JSON сохраняется; нормализация
для отображения не становится телом PATCH. Неизвестные блоки защищены.
EdTUI редактирует один блок; дерево и межблочные действия принадлежат zottion.

Миграции находятся в `migrations`, начальная схема — `001_initial.sql`.
Connection SQLite принадлежит отдельному потоку с очередью заданий. SQL-транзакции
не держатся во время сети. Межпроцессная блокировка профиля покрывает проверку
цели и отправку; миграция получает SQLite write lock до чтения user_version.
Снимки, поиск, черновики и операции имеют scope profile/workspace/credential.

## Запись и восстановление

Черновик → prepared → проверка изменяемых полей → sending → confirmed.
Расхождение даёт conflict, отказ — failed, неоднозначный ответ — unknown,
серверное задание — waiting. После аварии sending/waiting требуют сверки;
новый неидемпотентный запрос не отправляется автоматически. Известный ID задания
и ответ сохраняются в журнале; создание без известного ID проверяется вручную.
Подтверждение пишется до очистки черновика/обновления кэша.

При записи массивов свойств используется полное значение property-item API.
Предварительная проверка сравнивает изменяемые поля, но не обеспечивает CAS с
браузером. `--yes` подтверждает действие и не отключает проверки.

Сетевые задачи TUI возвращают сообщения с поколением экрана: устаревший ответ
не меняет текущую страницу. EditorState остаётся в UI-потоке. Локальный черновик
сохраняется при изменении текста; :w означает отдельную отправку в Notion.
Терминал восстанавливается RAII и panic hook, включая mouse/bracketed paste.

## Вход и поставка

Основной браузерный вход запускает официальный `ntn` как временный локальный
процесс: `login` → при необходимости `login poll` → `auth token --plain`.
Полученный токен проверяется через официальный `/users/me`, сохраняется в
системном хранилище zottion и используется его REST-клиентом. Общая OAuth
connection, наш домен и инфраструктура не нужны. `ntn` — отдельная зависимость
только для входа; данные страниц через него не проходят. Для CI и ограниченных
connections остаётся API-токен через stdin или NOTION_TOKEN.

Дополнительный `zottion-auth-service` сохранён для владельцев своей public
connection: явно выбранный сервер обменивает коды/refresh tokens и хранит
одноразовые сеансы в памяти. Он не является условием использования zottion.
Открытый файл ни в одном способе не подменяет системное хранилище.

`Cargo.lock` закрепляет зависимости; `rust-toolchain.toml` — Rust 1.91.0.
Ratatui 0.30, Crossterm 0.29, EdTUI 0.11.7. CI: fmt, Clippy, тесты и release.
Публикация архива и production-развёртывание выполняются отдельным действием.
